\subsection{Executive summary}

Grupo Pana sells vehicles through a channel called \emph{endoso}. Each sale passes through commercial, administrative, financial, documentation, customs, registration, preparation and delivery activities that require coordination between the customer and several employees. EndoTrack is a web platform that centralizes each operation from the official quotation to vehicle delivery.

The platform has two connected experiences:

\begin{enumerate}
	\item An \textbf{employee application} for managing customers, vehicles, sale registers, the 13-task process, documents, assignments, notes, reminders, audit history, exports and operational analytics.
	\item A \textbf{customer portal} where customers securely follow their own purchase through six customer-friendly milestones and access only the information and documents explicitly made available to them.
\end{enumerate}

Key characteristics of the product:

\begin{itemize}
	\item Each sale register represents exactly one vehicle; a customer buying two
	      vehicles has two independent sale registers.
	\item The internal process is a \textbf{strictly linear sequence of 13 tasks}; the customer sees a derived six-milestone view of the same sequence.
	\item Customer and vehicle-price snapshots are captured at sale creation and remain immutable; significant changes are recorded in an append-only audit trail.
	\item Authorization, task sequencing and document visibility are enforced by
	      the backend.
	\item The prototype must run at zero cost, so every component must offer a functional free tier.
\end{itemize}

The existing internal tools (a Power Apps application and a Power BI dashboard) are background context only; this document specifies the product described in the brief and does not aim to recreate them.

\section{Business Context, Problem Statement, Objectives and Scope}

\subsection{Business context}

Grupo Pana is a Peruvian automotive company and an official Toyota and Hino dealership that provides vehicle sales and other automotive services. A customer typically first contacts a sales advisor by WhatsApp or telephone and receives an initial, non-final quotation outside the tracked operation. If the customer decides to proceed, the advisor creates the sale register and the formal process starts with Task~1, the official quotation. The initial informal quotation is not a task and is outside the system. \tagconf{}

\subsection{Problem statement}

Endoso operations require coordination among customers and employees across many steps, and the current tooling is basic. The brief lists the following \emph{potential} problem areas: operational coordination, traceability, delays, bottlenecks, document management, customer uncertainty, data quality and management reporting. \tagconf{} These are hypotheses to be validated during analysis rather than proven problems. \tagassm{}

\subsection{Record provenance}

For customers, employees, vehicle catalog records (models, versions, colors,
images) and sale registers, the platform tracks \code{created_at},
\code{created_by}, \code{updated_at}, \code{updated_by} where applicable, and

\section{The 13-Task Operational Lifecycle}

\subsection{Status model and strict linear transition rules}

Each task has exactly one of three statuses: \code{pending}, \code{in_progress},
\code{completed}. \tagconf{}

\begin{itemize}
	\item The process is strictly linear. Task~1 is the only task eligible to start initially; Task~$N$ may move from \code{pending} to \code{in_progress} only after Task~$N-1$ is \code{completed}. \tagconf{}
	\item Parallel tasks, branches and out-of-order completion are not allowed in
	      the normal workflow; at most one task is \code{in_progress} per sale. \tagconf{}
	\item The current active task is the single \code{in_progress} task; if none exists, the next eligible task is derived from the ordered statuses. \tagconf{}
	\item No dependency table or graph is introduced for the linear process unless a future requirement justifies branching. \tagconf{}
	\item A confirmation message is shown before any task status change, especially completion. \tagconf{}
	\item All backend endpoints, not only UI controls, enforce sequencing, required data, uniqueness and permissions. \tagconf{}
\end{itemize}

\begin{longtable}{@{}L{3.3cm}L{3.3cm}L{4.0cm}L{5.2cm}@{}}
	\toprule
	\textbf{Transition}                               & \textbf{Allowed actors}            & \textbf{Preconditions}                                           & \textbf{Notes}                                                                                               \\
	\midrule
	\endhead
	\code{pending} $\rightarrow$ \code{in_progress}   & Advisor (own sale), Manager, Admin & Task $N-1$ is \code{completed} (Task~1: sale is \code{active})   & Records start timestamp; due date is computed here (Section~\ref{sec:sla}); confirmation required.           \\
	\code{in_progress} $\rightarrow$ \code{completed} & Advisor (own sale), Manager, Admin & All required fields and documents present; validations pass      & Records completion timestamp and \code{completion_phase}; may trigger a notification; confirmation required. \\
	\code{completed} $\rightarrow$ \code{in_progress} & Manager, Admin only                & Task is the \emph{most recently completed} task; reason recorded & No cascading rollback; fully audited.                                                                        \\
	\code{in_progress} $\rightarrow$ \code{pending}   & \tagopen{}                         & \tagopen{}                                                       & Not specified in the brief; see Appendix~\ref{app:open}.                                                     \\
	\bottomrule
\end{longtable}

\subsection{Task data and editing rules}

\begin{itemize}
	\item Every task has an optional Notes textarea. \tagconf{}
	\item Every non-optional field or document is required before the task can be completed. \tagconf{}
	\item All task fields and document uploads are disabled and read-only until the task becomes \code{in_progress}. \tagconf{}
	\item Unique constraints specified per task must be enforced. \tagconf{}
	\item After completion, only a Sales Manager or System Admin may modify fields or documents; Sales Advisors see completed tasks read-only. \tagconf{}
	\item \textbf{Data correction:} Managers and Admins may edit fields or replace documents of a \code{completed} task without changing its status; every such edit requires a mandatory ``Reason for Edit'' and is recorded in the append-only audit log. \tagconf{}
	\item \textbf{Accidental completion:} only the most recently completed task may be reverted to \code{in_progress}. To reopen Task~4 while Task~6 is active, a manager must revert Task~6, then Task~5, then Task~4. This friction is intentional to protect data integrity and customer milestone visibility. \tagconf{}
	\item The recommended duration is the elapsed time from \code{in_progress} to \code{completed}; tasks without a recommended duration have no predefined duration. \tagconf{}
\end{itemize}

\subsection{Financial reconciliation rules}

All amounts are USD. Let $Q$ be the \emph{quoted final vehicle price} of Task~1, $T_0$ and $C_0$ the initial Toyota amount and commission, $A$ the accessory amount, $R$ the vehicle release processing amount, and $T_1$, $C_1$ the final Toyota amount and commission (Task~3).

\begin{longtable}{@{}L{1.2cm}L{14.6cm}@{}}

	\textbf{Rule} & \textbf{Definition}                                                                                                                                                                  \\
	\midrule
	\endhead
	F1            & Task~1: $Q = T_0 + C_0 + A + R$ (calculated). $T_0$ and $C_0$ are provisional; $A$ and $R$ stay constant for the whole operation. \tagconf{}                                         \\
	F2            & Task~3: the quoted price does not change. $C_1 = Q - (T_1 + A + R)$, so that $T_1 + C_1 + A + R = Q$. \tagconf{}                                                                     \\
	F3            & Task~4: the deposited amount is expected to equal $Q$. \tagconf{}
	\tagopen{} Whether a mismatch blocks completion or requires a documented
	reason.                                                                                                                                                                                              \\
	F4            & Task~5: the deposited amount is expected to equal $T_1$. \tagconf{}                                                                                                                  \\
	F5            & Task~6: invoice amounts are expected to equal $T_1$ (Toyota), $C_1$ (commission), $A$ (accessories) and $R$ (release processing). \tagconf{} The four invoices therefore sum to $Q$. \\
	F6            & \tagprop{} Store money as exact decimals (for example two decimal places),
	never floating point; define a rounding rule. \tagopen{} If $C_1$ would be
	negative (that is, $T_1 + A + R > Q$), whether to block, or require manager

\subsubsection*{Permission design requirements}
\begin{itemize}
	\item Authorization is enforced in the backend/API, with least privilege by
	      default. \tagconf{}
	\item Viewing is separated from modifying, cancelling, reopening, exporting
	      and deleting. \tagconf{}
	\item Security-sensitive actions, overrides, cancellations, role changes and exceptional deletions are logged. \tagconf{}
	\item Prefer soft deletion/archival; permanent removal requires confirmation and an audit trail. \tagconf{}
\end{itemize}

\subsubsection*{Concerns and proposed resolutions}
\begin{itemize}
	\item \tagopen{} \textbf{Advisor customer access.} Advisors may create
	      customers but view only customers tied to their own sales; a newly created
	      customer has no sale yet, and a uniqueness conflict on document number reveals
	      that a customer exists. \tagprop{} Treat customers created by the advisor as
	      accessible, and offer a controlled ``attach existing customer'' flow that
	      exposes minimal data.
	\item \tagopen{} \textbf{Reassignment.} Whether access changes immediately when a sale is reassigned (proposal: yes, access follows the current assignee; history stays in the audit trail).
	\item \tagprop{} \textbf{Admin destructive power.} Require a reason, an
	      explicit confirmation and an audit event for permanent deletion; consider a
	      restricted time window or two-person approval later.
\end{itemize}

\subsection{Authentication}

\begin{itemize}
	\item \textbf{Two interfaces and routes:} employees at \code{/admin} (document
	      types DNI, CE, PAS) and customers at \code{/portal} (DNI, CE, RUC, PAS, CDI).
	      \tagconf{} Separate pages are for usability and routing only; identity, user
	      type, role and resource authorization are enforced by the backend. \tagconf{}
	\item \textbf{Login fields (both):} document type, document number, password, a ``Forgot password'' link and a ``Keep me signed in'' checkbox. Email is not the login identifier. \tagconf{}
	\item \textbf{Validation:} document format depends on the selected type (for example DNI typically eight digits, RUC eleven), configurable and validated on both client and server. \tagconf{}
	\item \textbf{Uniqueness:} composite unique \code{(document_type, document_number)} in both the customers and employees tables, normalized consistently while preserving leading zeros. \tagconf{}
	\item \textbf{Same person in both tables:} the authentication system must
	      distinguish account types and prevent cross-portal leaks. \tagprop{} Separate
	      account namespaces, a mandatory \code{user_type} claim and token audience, and
	      separate cookie names/paths.
	\item \textbf{Sessions:} short-lived JWT access tokens and long-lived refresh tokens in HTTP-only cookies, with a Remember Me option. \tagconf{} \tagprop{} Add \code{Secure} and \code{SameSite} flags, refresh-token rotation and revocation, CSRF protection where applicable, logout invalidation and session expiry; JWT alone is not a complete strategy.
	\item \textbf{Passwords:} never stored in plain text; use a modern
	      password-hashing algorithm. \tagconf{}
	\item \textbf{Access logs:} an append-only \code{AccessLogs} table records
	      \code{user_type}, attempted document type/number, \code{user_id} when
	      identified, \code{action_type} (\code{LOGIN_SUCCESS}, \code{LOGIN_FAILED},
	      \code{LOGOUT}), IP address where reliable, and timestamp. No secrets or
	      passwords are logged. \tagconf{}
\end{itemize}

\section{Data Provenance, Event Auditing and Notification Engine Rules}

\subsection{Append-only audit trail}\label{sec:audit}

The audit trail is distinct from provenance fields and from authentication access logs. It is append-only for ordinary roles, and it avoids storing passwords, tokens, full document contents or unnecessary sensitive data. \tagconf{} Each event records the actor, target entity and record id, event/action type, timestamp, and an appropriate before/after summary. \tagconf{}

\begin{longtable}{@{}L{4.4cm}L{11.4cm}@{}}
	\toprule
	\textbf{Event class} & \textbf{Minimum coverage}                                                                                                              \\
	\midrule
	\endhead
	Task status changes  & Previous/new status, actor, timestamp, reason where
	applicable.                                                                                                                                                   \\
	Sale state changes   & Cancellation, reopening, completion changes, and the reason for cancellation/override.                                                 \\
	Assignment           & Assignment and reassignment of Sales Advisors.                                                                                         \\
	Field changes        & Important changes to sale, customer, vehicle/catalog and task fields; edits to completed tasks with the mandatory ``Reason for Edit''. \\
	Documents            & Uploads, replacements, archival/deletion and visibility changes.                                                                       \\
	Security             & Role/permission changes and other security-sensitive administrative actions, including permanent deletions.                            \\
	\bottomrule
\end{longtable}

\tagopen{} Access restrictions and retention periods for audit logs and access logs.

\subsection{Notification engine rules}\label{sec:notif}

\begin{itemize}
	\item Notifications must be reliable and idempotent: no duplicates if a task transition is retried, a scheduler runs twice, or an event is replayed. \tagconf{}
	\item Delivery attempts and outcomes are stored. \tagconf{}
	\item Sensitive documents are not attached to emails; secure authenticated
	      links are used instead. \tagconf{}
	\item \tagprop{} Use a transactional outbox: the notification is written in the same database transaction as the task transition, then delivered asynchronously with retries; a unique key per sale, event type and recipient provides deduplication.
	\item \tagopen{} If a task is reverted and completed again, whether the customer email is resent (proposal: no resend; the portal shows the corrected state).
\end{itemize}

\subsection{Task deadlines, reminders and escalation}\label{sec:sla}

\begin{itemize}
	\item \textbf{Due date:} computed when a task goes from \code{pending} to \code{in_progress} by adding the recommended duration to the start timestamp, in strict elapsed calendar time (weekends and non-business hours do not pause the clock). Example: a three-day task started Friday 4:00~PM is due Monday 4:00~PM. \tagconf{}
	\item Tasks without a recommended duration receive no duration-based reminders. \tagconf{}
	\item \textbf{Approaching Due:} one warning when 80\% of the recommended duration has elapsed (for the three-day task, after 57.6 hours). \tagconf{}
	\item The platform never automatically unlocks or reassigns a task because it is overdue. \tagconf{}
\end{itemize}

\begin{longtable}{@{}L{5.2cm}L{4.6cm}L{6.0cm}@{}}
	\toprule
	\textbf{Level}                            & \textbf{Recipient}     & \textbf{Additional behavior}         \\
	\midrule
	\endhead
	Level 1: warning through 24 hours overdue & Assigned Sales Advisor & Visible indicator.                   \\
	Level 2: 24 to 48 hours overdue           & Sales Manager          & Escalation indicator.                \\
	Level 3: more than 48 hours overdue       & System Admin           & Task visually highlighted in the UI. \\
	\bottomrule
\end{longtable}
\tagconf{} \tagopen{} Whether ``Sales Manager'' and ``System Admin'' mean all holders of the role or a designated person.

\textbf{Recurring reminders.} Frequency depends on the recommended duration (shorter tasks remind more often) with a hard cap; the exact intervals and cap are to be confirmed before implementation. \tagconf{} \tagprop{} Initial proposal: tasks of at most 3 days every 12 hours; tasks of 10--15 days every 24 hours; the 30-day task every 48 hours; at most 6 recurring reminders per task.

\textbf{Deduplication state and logging.} Track \code{last_reminder_sent_at},
\code{current_reminder_phase} (\code{approaching}, \code{overdue},
\code{recurring}) and \code{recurring_reminder_count}; record every dispatched
reminder in an append-only \code{Notification_Log} (or equivalent). \tagconf{}

\textbf{UI and analytics.} Show indicators for \emph{Approaching}, \emph{Overdue} and \emph{Escalated/Recurring}, with quick filters for urgent tasks. \tagconf{} Store \code{completion_phase} on completion with values \code{early}, \code{in_approaching}, \code{overdue} or \code{recurring_overdue}. \tagconf{} \tagopen{} Value of \code{completion_phase} for tasks without a recommended duration (proposal: null).

\subsection{File and document management}\label{sec:files}

The platform must support secure upload, validation and storage; MIME type and size in bytes per upload; original file name, upload timestamp, uploader and task/sale association; replacement behavior with version history where needed; deletion/deactivation rules with audit history; defined maximum size and formats; role-based upload, update and download permissions; explicit per-field/document customer visibility; authenticated or time-limited access; and safe behavior when a stored file is missing. \tagconf{} The database stores metadata and storage references rather than file contents. \tagconf{} Private documents must never be exposed merely because a URL is known. \tagconf{} \tagopen{} Maximum file size and allowed formats (proposal: PDF, plus Excel for the Task~1 quotation; a size limit to be set from storage quotas).

	Fully relational (one table per task type) & Strong typing, native unique and foreign-key constraints, easy reporting                    & More tables and migrations; changes to a task need schema changes                 & Strong for constrained and reported fields \\
	Single JSON column                         & Flexible, few tables                                                                        & Weak constraints (uniqueness, amounts), harder reporting, validation only in code & Risky for this domain                      \\
	Hybrid                                     & Typed columns/tables where integrity or reporting matters; JSON only for informational data & Two patterns to maintain                                                          & Leading candidate                          \\
	\bottomrule
\end{longtable}

\tagprop{} Provisional direction: a hybrid in which values that need uniqueness, arithmetic reconciliation or reporting (amounts, series, VIN, transaction and invoice numbers, plate, dates, enumerations) are typed relational columns, with a common task-instance table, a generic document table and an ordered task-definition table. This will be settled in an ADR during data modeling.

\subsection{Backend and frontend structure}

\tagprop{} Modular monolith with layered, feature-oriented modules (presentation, application, domain, infrastructure).

\begin{verbatim}
endotrack/
  apps/
    api/                      # Express + TypeScript
      src/
        modules/
          auth/ customers/ employees/ catalog/
          sales/ tasks/ documents/ notifications/ analytics/
            (each: http/ application/ domain/ infrastructure/)
        shared/               # errors, validation, logging, config
        jobs/                 # scheduler tick, outbox dispatcher
      tests/
    web/                      # React + TypeScript
      src/
        features/             # per-module UI, hooks, API clients
        components/ routes/ lib/
  packages/
    contracts/                # shared Zod schemas and types
  docs/ (adr, erd, api)
\end{verbatim}

Candidate patterns: repository and unit-of-work for persistence, a task state machine in the domain layer, policy objects for authorization, outbox for notifications, and a strategy/adapter for storage and email providers. \tagprop{}

\subsection{Key technical risks}

\begin{itemize}
	\item Free-tier behavior (sleeping API, expiring or pausing databases, storage quotas) conflicts with scheduling and confidential-file requirements; mitigated by the scheduler design and storage abstraction above.
	\item Strict-sequence integrity under concurrent updates requires transactional checks and database-level constraints in addition to application logic.
	\item Confidential identity and financial documents require a storage and retention policy reviewed for legal compliance.
\end{itemize}
