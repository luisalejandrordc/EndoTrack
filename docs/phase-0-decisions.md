# Phase 0 — Decisions

These are the decisions made based on the open questions and edge-cases detected by the LLM during the project's Phase 0.

### A. Contradictions and inconsistencies

1. **Password hashing.** Use Argon2id with parameters tuned to the free Render instance's memory.
2. **Refresh-token design.** Keep two tables for `refresh_tokens` with real FKs. The cleanup job must clean both of them. Add rotation and reuse-detection fields (token family, revoked/replaced timestamps, remember-me flag).
3. **Managers and sale creation/editing.** Managers and admins can create sales and assign an advisor to them at creation. When an advisor creates a sale, they get automatically assigned to it.
4. **Editing completed tasks vs derived money.** Block edits to financial source fields while any dependent task is completed. Require downstream tasks to be rolled back in reverse order before editing. Allow other edits with a Reason for Edit.
5. **Reopen vs “one `in_progress`”.** Allow reopening only when no task is `in_progress`. After a task gets reverted to `pending` its data and files entered stay (read-only) rather than being cleared.
6. **SLA state on reopen, restart and cancel.** Reset reminder counters and SLA phases on task restart. Preserve them on reopen so the reminder cap isn’t re-armed. When reopening a cancelled sale, resume SLA clocks with the remaining time rather than counting cancelled time as delay.
7. **PDF generation** Treat PDF generation as a future enhancement, not part of the current scope. All PDFs in the initial release are uploaded documents.
8. **Notification scope.** Limit notifications to email for MVP/V1. Trigger Notification 1 whenever an account is created, regardless of whether the actor is a Sales Advisor, Manager, or Admin.

### B. Business rules and workflow

9. **Who starts tasks?** Keep task initiation manual while recording when each task becomes eligible. A task becomes eligible as soon as the previous task is completed, following the strict linear sequence. Eligibility does not automatically start the task.
10. **Sale cancellation and reopening.** Allow cancellation based on role and task stage: Advisors may cancel while the active task is between 1 and 3, Managers until Task 6, and only Admins after Task 6 is completed. Completed sales cannot be cancelled. Store a required cancellation category and free-text reason as first-class sale fields, not only in the audit log, to support BI reporting. Require a reason when reopening a cancelled sale. Keep cancellation and reopening reasons internal; do not expose them to customers.
11. **Vehicle changes, sale snapshots, and temperature.** Lock the vehicle model, version, and color after sale creation. To correct them, cancel and recreate the sale, or allow a Manager-only audited correction before Task 3. Snapshot `customer_type` at sale creation because Task 2’s Vigencia de Poder requirement depends on it; keep categories and catalog images live. The actor who creates the sale sets its temperature. Show an indicative conversion-probability hint: Hot ≈ 70% or more, Warm ≈ 30–69%, and Cold below 30%. Store only the temperature label, without enforcing percentage thresholds, so BI can measure actual conversion rates for each label.
12. **Amount reconciliation.** Apply the Mismatch-Reason mechanism wherever an amount is expected to match, including Task 5 versus Task 3 and the Task 6 invoices. Require a recorded mismatch reason whenever amounts differ, rather than automatically blocking completion. Enforce exact amount matching without IGV adjustments, treat each payment as a single deposit, and use USD exclusively.
13. **Zero amounts.** Require accessories, release processing, commission, and amount payable to Toyota to be strictly positive. Since zero amounts are not allowed, the corresponding Task 6 invoices and Task 12 service order remain mandatory.
14. **Uniqueness scope.** Enforce uniqueness across all records, including cancelled sales, for bank and transaction numbers, invoice numbers, and DAM numbers. Task 4 and Task 5 transaction numbers use separate uniqueness scopes. Normalize identifiers for case and whitespace before checking uniqueness. Enforce the series identifier format strictly as the full series, a hyphen, and the correlative number.
15. **Controlled lists.** Maintain the initial bank and customs-office lists through the developer, using the previously specified banks and including Marítima del Callao and Chancay as customs offices. Task 9’s “person in charge” is free text, not an employee reference. Define document types as representative names for the files required by each task, inferring the complete set from the task specifications and examples. Each document type can hold exactly one file per task.
16. **Validation rules.** Enforce the specified identification formats: DNI must contain exactly 8 digits, RUC exactly 11 digits, CE exactly 9 alphanumeric characters, PAS 6–12 alphanumeric characters, and CDI 8–12 alphanumeric characters. Validate VINs and Peruvian license plates against their applicable formats. Invoice number pattern: 4 alphanumeric characters, a hyphen, then 1–8 digits (e.g. `F001-000123`) Hard-block impossible or invalid values, including values outside defined monetary limits. Allow future dates where valid, but display soft warnings when dates are out of chronological order across tasks rather than blocking completion.
17. **DDC/PEP.** Record `PEP`, `Relacionado con PEP`, and `Reforzado` as informational fields only. These flags do not trigger blocks, additional approvals, or alerts. No separate compliance role is required; access remains limited to the existing Advisor, Manager, and Admin roles.
18. **What customers see, and when.** Expose task data to customers only after the corresponding task reaches `completed`. Do not expose data entered while a task is `in_progress` or `pending`. When a task is reverted and progress moves backward, reflect the regression honestly in the customer-facing progress tracker without exposing incomplete or reverted task data.
19. **Advisor contact exposure.** Store only business email and phone number for employees; the phone number also serves as their WhatsApp contact, so no separate WhatsApp field is needed. When a sale’s assigned advisor changes, notify the customer by email through a new Notification 10: Advisor Assignment Change.
20. **Customer accounts.** Add an `is_active` flag to customer accounts to control portal access; inactive accounts cannot log in. Require an email address for each customer account, but do not enforce email uniqueness. For B2B customers, use a single shared login per entity rather than separate accounts for individual contacts.
21. **Advisor access to customers.** An advisor who creates a customer retains access to that customer until the first sale is created. For existing-customer lookups, advisors who are not linked to the customer may see only the customer's legal name. Rate-limit and audit-log all lookups to prevent abuse and support traceability.
22. **Employee lifecycle.** Employees follow the same onboarding process as customers: they receive a provisional password by email to their business email address and must change it at first login. When an employee account is deactivated, block the action if the advisor has active sales until all those sales have been reassigned. Allow multiple Admins, but prevent deactivation of the last active Admin account.
23. **Audit visibility and permanent deletion.** Log all data exports in the audit trail. Restrict history visibility by role: Advisors can view the timelines of their assigned sales; Managers can view all sales history and customer and catalog changes; Admins can view all history, including employee and security events. Restrict access logs to Admins only. Allow hard deletion only for test or corrupted sales that have never reached delivery, while preserving all associated audit records. Records with existing history must be deactivated rather than permanently deleted.
24. **Retention and privacy law.** Defer retention periods for identity documents, invoices, and logs, as well as data-subject requests under Peru’s data-protection law, to a future legal review.

### C. Security and authentication

25. **Temporary password by email (§6.4, Notification 1).** Emailing a plaintext password is weak. **Rec:** use a single-use, short-lived activation link. If you keep the temp password, define its expiry (e.g. 72 h) and a resend policy.
26. **Auth policy gaps.** Login throttling and lockout are unspecified, as are generic error messages. Rotation resets 30 days each time, so there is no absolute session limit. The server-side lifetime for non-“remember me” sessions is undefined. Two tabs refreshing at once can cause a false reuse detection. Role and deactivation changes could stay stale for up to the 15-minute JWT lifetime. **Rec:** lockout after repeated failures, and an absolute maximum session (your call on the length). Also check active status and role in the DB on every request, and revoke refresh tokens on deactivation or password reset.
27. **Codart API.** I need its documentation, auth method, quota, terms and sample responses. It is a third-party source of personal data, so is it approved by Grupo Pana and legal? Lookups cover DNI and RUC only, so CE, PAS and CDI are always manual. Does it also prefill Task 2 signer names? **Rec:** log lookups, rate-limit per user, and mark names “looked up” vs “manually entered”.

### D. Platform and free-tier risks (items marked “verify” are from memory and I’ll confirm them in a spike)

28. **Cross-site refresh cookie (potential blocker).** The static site and API will sit on different `onrender.com` subdomains. I believe browsers treat those as cross-site (verify), so the HttpOnly cookie would need `SameSite=None`, which browsers increasingly block. It would also need CSRF defense. The options are:

    - (a) proxy `/api` through the static site’s rewrite rules to make it same-origin;
    - (b) a shared custom domain;
    - (c) a different token strategy.

    **Rec:** test (a) first. Either way this touches §14.3, so I need your approval. Do you have a Grupo Pana domain we could use?

29. **Render free tier and production plan.** Free services sleep when idle (verify), which affects demos, first logins and cron-job.org’s request timeout. That is fine for development. When does zero-cost end, and what is the production budget? Please share the expected workload (employees, concurrent users, sales per month, documents per sale, file sizes) so I don’t guess the NFR targets.
30. **Scheduler and reminders.**
    - (a) Twice-daily cron against a 12-hour cadence and a 57.6 h warning on Task 2 means reminders can arrive up to a run late. **Rec:** an hourly trigger with idempotent evaluation.
    - (b) Is there a first “overdue” notice at `due_date`, and does “first overdue recurring reminder” mean count 1? What happens after the cap of 6: silence, or UI highlight only?
    - (c) Do Level 2 and 3 go to all active Managers and Admins? Is the advisor copied? What if none exist?
    - (d) What are the `completion_phase` boundaries? **Rec:** compute them from timestamps, not from reminders actually sent.
31. **Email.** Resend needs a verified sending domain. Who controls DNS for Grupo Pana’s domain? Without it we can only send tests to the account owner. The free tier may also have a daily cap (I recall about 100/day; verify), which matters for reminder volume. **Rec:** non-production environments must never email real addresses.
32. **R2.** It may require a payment method on file even for the free allowance (verify). Is that compatible with “zero cost”? Public `r2.dev` URLs are meant for development, so production public images need a custom domain. §15 treats profile images as public, which would expose employee photos. **Rec:** public only for catalog images, with employee photos private and signed. Do uploads stream through Go or use presigned URLs? What are the maximum size and allowed formats, and is malware scanning needed?
33. **Supabase.**
    - (a) Tables are exposed through its auto-generated API by default. Only Go touches the DB, so **Rec:** disable that API and apply deny-all RLS on every table.
    - (b) Connection mode: pooler vs direct, IPv6, and prepared statements with pgx behind a transaction pooler.
    - (c) There is no managed point-in-time recovery on the free tier (verify), but the NFRs need backup and recovery. **Rec:** a scheduled `pg_dump` to R2 from a free GitHub Actions job.
    - (d) The 500 MB cap against audit, access and notification log growth.
