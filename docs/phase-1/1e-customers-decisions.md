# 1E customers module: implementation decisions

Status: customers, existence lookup and Codart lookup are implemented and tested. The vehicle catalog is the remaining 1E module.

| #   | Decision                                                                                                                                                                                                             | Why                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Advisor scope is one SQL rule: a sale currently assigned to the advisor, or created by them with no sale yet. Customers outside scope answer 404, not 403.                                                            | FR-026. A 403 would confirm the customer exists.                                                                                 |
| 2   | The existence lookup returns `access: full` (record) or `access: name_only` (id, legal name, type, active flag). The name-only answer carries no document, contact data or sale information.                         | Permission matrix: unlinked advisors see the legal name only.                                                                    |
| 3   | Editing a name without sending `nameSource` marks it `manual`. A phone or email edit keeps `looked_up`.                                                                                                              | Provenance must stay truthful (solved question 27).                                                                              |
| 4   | The audit entry for an edit records name and document changes with before and after values, but only "changed" for phone, email and contact names.                                                                   | Contact data is personal data; the audit trail must not become a second copy of it.                                              |
| 5   | `GET /lookups/identity` checks our database first. A known customer is answered from it (source `database`) and is logged as `customer_existence`, so it never counts against the Codart quota.                      | FR-024.                                                                                                                          |
| 6   | The quota counts `success`, `not_found` and `error` calls in the current Lima month. Blocked and throttled requests do not count. Peru has no daylight saving time, so Lima is a fixed UTC-5 offset.                | A failed call may still be billed; being conservative protects the 110-request allowance.                                        |
| 7   | The quota check and its reservation run in one transaction under a PostgreSQL advisory lock. The reservation is a log row marked `error` until the real outcome is known.                                            | Two simultaneous requests cannot both take the last unit. If the process dies mid-call, the unit stays counted.                  |
| 8   | Rate limits are per employee per minute (20 by default), read from `lookup_logs`, so they survive restarts and work across instances. Refused requests are logged but do not extend the lockout.                     | The in-memory limiter in `httpx` is per process.                                                                                 |
| 9   | Every identity lookup failure uses a distinct code (`IDENTITY_NOT_FOUND` 404, `LOOKUP_QUOTA_EXHAUSTED` 409, `RATE_LIMITED` 429, `LOOKUP_UNAVAILABLE` 503). The frontend unlocks manual entry on any of them.        | FR-023 manual fallback.                                                                                                          |
| 10  | Without `CODART_TOKEN` the server starts, logs a warning and answers `LOOKUP_UNAVAILABLE`.                                                                                                                           | Local development and tests never need the real provider.                                                                        |
| 11  | Deactivating a customer blocks new sales and portal access later; it does not revoke sessions yet because customer sessions arrive with the portal (Phase 2).                                                        | Nothing to revoke before then.                                                                                                   |
